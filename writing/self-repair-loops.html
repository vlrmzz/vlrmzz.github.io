Self-repair loops for coding agents: does running the tests make the code correct?

22 October 2026 · My agent's tests passed. The code was still wrong.

Code on GitHub

I gave a coding model a simple loop: write the code, run the tests, and if they fail, read the errors and fix the code. In 90 of 100 runs, the loop got the tests to pass. Only 48 of those programs were correct.

The tests were not wrong. They were just few, like the tests most people write first. The loop did exactly what it was built to do: it made them pass. To see whether the code was right, I kept back 224 more tests that the loop never saw.

I repeated this on three small models and ten tasks, for $1.44. Every loop made its own tests pass far more often than it made the code correct. The 90 against 48 above is the widest gap of the five loops; the narrowest was 97 against 87.

The claim

A popular claim says that a simple verification loop makes a coding agent much better: generate, run the tests, and on failure let the model critique and fix its code. Research systems such as Reflexion, Self-Debugging and AlphaCodium build on this idea, and most coding agents run some version of it.

The catch is in the word “success”. A loop stops when its tests pass, so by its own measure it always succeeds. The real question is whether passing the loop's tests means the code is correct.

The gap between passing tests and correct code is not new. EvalPlus (Liu et al., 2023) added many more tests to the HumanEval benchmark, and the pass rates of the models it tested went down. A benchmark with few tests overrates a model. This post asks the same question of a loop, which is built to make its few tests pass.

Hypothesis

  • A loop over a few given tests helps, but less than the claim says, because it can only fix the bugs those tests show.
  • A loop where the model first writes its own tests helps more, because it checks more of the specification.
  • Both loops sometimes stop with their tests passing and the code wrong.

Setup

Ten tasks, two sets of tests

Each task is one Python function with an exact specification: a SemVer sorter, a glob matcher, a cron scheduler, an expression evaluator, an ISO 8601 duration parser, a strict Roman numeral parser, a byte formatter, a strict CSV parser, a smallest longest-common-subsequence, and an LRU cache with expiry. Each has a few rules that are easy to miss.

  • Visible tests, 36 in total: the examples from the prompt and one or two more. A loop may see these.
  • Held-out tests, 224 in total: the rest of the specification. No loop sees them. They only score the final code.

Here is part of the evaluator task. The prompt states the rule about -2^2. No visible test checks it.

# prompt.md (excerpt)
Unary - binds more loosely than ^, so -2^2 is -(2^2) = -4.

# tests.py (excerpt)
CASES = [                       # visible: the loop sees these
    (("1 + 2 * 3",), "7"),
    (("2 ^ 3 ^ 2",), "512"),
]
HIDDEN = [                      # held out: only for scoring
    (("-2^2",), "-4"),
    (("2^(1/2)",), ValueError), # must raise
]

The expected values come from reference solutions that the model never sees. Two of them I also checked with a brute force.

Three conditions

  • Baseline: one answer.
  • Harness: run the visible tests; on failure, send back the code and the test output, and ask for a short diagnosis and a fixed version. At most 3 attempts.
  • Self-test harness: first, in a separate call, the model writes its own test cases from the specification, without seeing any code. The loop then runs the visible tests plus those. This is closer to Reflexion and AlphaCodium.

The loop is a few lines. This is the core of run.py, simplified:

attempts = [attempt(first_prompt(task))]
if condition != "baseline":
    # stop when the loop's own tests pass, or after 3 attempts
    while not attempts[-1].passed_loop and len(attempts) < 3:
        last = attempts[-1]
        prompt = repair_prompt(task, last.code, last.feedback)
        attempts.append(attempt(prompt))
# the only score: visible plus held-out tests
success = run_tests(attempts[-1].code, visible + held_out)

The feedback is the test runner's output, such as FAIL parse_csv_line('a,,'): expected ['a', '', ''], got ['a', ''].

Three small, cheap models ran every task 10 times in every condition: Claude Haiku 4.5 through the Claude Code command line, with tools and thinking off; DeepSeek V4.1 Flash through OpenRouter, reasoning off, temperature 0.2; and GLM 5.3 Flash through OpenRouter, temperature 0.2, where the provider does not allow reasoning to be switched off. Haiku did not run the self-test harness, which I added later.

The p-values are exact McNemar tests against the baseline, on the same task and repeat. The last column is the noise check. Each loop's first attempt is a fresh baseline, and it drifted by up to 7 points. A gain smaller than that is chance. So the plain harness did little for Haiku and DeepSeek and a lot for GLM, and the self-test harness was the best condition for DeepSeek.

GLM's large gain is mostly not about tests. GLM sometimes reasons until it reaches the output limit of 8,000 tokens and then writes no code at all: 57 of its 425 answers were empty. The loop repairs most of them by asking again, which any retry would do. In the plain harness, test feedback itself repaired 3 to 9 runs in 100.

Three runs, close up

A rule that no test checks. Haiku's evaluator passed all 5 visible tests on the first try, so the harness stopped. The held-out tests then failed on -2^2: it returned 4, not -4. The prompt states this rule in words. That case failed in 16 of Haiku's 17 failed runs on this task, and the harness never found out.

An empty answer. On the subsequence task, GLM's baseline was correct in 1 run of 10 and its harness in 10 of 10. In all 8 runs that the harness repaired, the first answer was empty, and the feedback was No code block found in the reply. No test was involved.

A wrong test written by the model. DeepSeek wrote 28 tests for the evaluator; 27 were right. The wrong one expected 2 ^ 1/2 to raise an error, as if it meant 2 to the power of one half. By the specification it is (2^1)/2 = 1, and the first code was correct. The loop “fixed” it to raise the error, and the change broke 2^64 / 2^62 in the held-out tests.

The model's own tests

The self-written tests were mostly right: 96 % of DeepSeek's 2,997 cases and of GLM's 1,746. But only about half of the test files were right in every case (34 of 72 usable files, and 35 of 65), and one wrong case keeps a loop going. Both models also wrote far more cases than the 10 to 25 I asked for, and often ran out of output tokens before the list was finished. Those runs fell back to the visible tests. The self-test harness cost about 4 times the baseline; the plain harness about 1.3 to 1.5 times.

What this means if you build agents

  • Score the loop on tests it never sees. Its own pass rate said 90 % where the truth was 48 %. Keep a held-out set, even a small one, and report both numbers.
  • A loop can only fix what its tests check. A rule stated in the specification but not tested, like -2^2, stays broken. If something matters, turn it into a test.
  • Separate retry from repair. Before you credit the tests, add a plain retry for empty or cut-off answers and check the stop reason. Much of one model's gain was exactly that.
  • Let the model write tests, but do not trust them blindly. Ask for them from the specification, before the code. Expect a few to be wrong, tell the repair step that the specification wins, and cap the attempts. Watch for loops that rewrite code that was already correct.
  • Watch the output budget. A model that reasons can spend its whole limit thinking and return nothing.
  • Price it. Here a plain loop added 30 to 50 % to the cost, and a self-test loop multiplied it by about 4. That is worth it where a wrong answer is expensive.

What about frontier models?

These are small models on purpose: they fail often enough for a loop to have work. Frontier models reason before they answer, and that reasoning is already a check of its own. I saw this by accident. With Claude Code's default thinking on, Haiku's one-shot answers used about 15,000 output tokens for a reply of about 800, and its baseline passed 9 of 10 hard tasks in a pilot. With thinking off, it passed 8 of 20. For a model that reasons, the useful question is what the loop checks that the reasoning cannot: running the code, and behaviour that no visible test covers.

How I got here

The first version could not answer the question. On ten textbook tasks, Haiku passed 29 of 30 runs at once, so there was nothing to fix. It was also thinking in secret, as above. And the loop saw every test with its expected value, so a repair could copy the answer. The harder tasks, thinking switched off and the held-out tests came from those three problems. One GLM run also crashed at run 231 of 300 on a dropped connection and wrote nothing; I ran it again. Its log shows the same gains at a lower level: 37 % for the baseline, 57 % and 64 % for the loops.

Choices and trade-offs

  • One message per attempt, not a chat. Each repair prompt holds the task, the last code and the test output. That is the same for every model and easy to log, but the model does not see its earlier reasoning.
  • The model's tests see no code. Otherwise it tests what the code does, not what the specification says. The price: the tests are blind to the code's weak points.
  • At most 3 attempts. The third attempt added 0 to 4 points, except in DeepSeek's self-test loop, which went from 77 % to 87 % on it.
  • 8,000 output tokens. Enough for every task, but not for a model that reasons at length. A higher limit would have raised GLM's baseline and shrunk its loop gains.
  • Temperature 0.2 and a $2 cap. The runner stops when the reported cost reaches a limit and keeps only whole repeats. Through the Claude Code command line, temperature cannot be set.

Conclusion

Two expectations held and one held in part. A loop over a few given tests helped less than the claim says: within noise for two models, and for the third mostly through retries. Writing its own tests first was the best loop for DeepSeek and as good as the plain loop for GLM, at about 4 times the cost. And every loop stopped, in 8 to 42 runs in 100, with its tests passing and the code wrong.

So the claim holds in a weaker form. A verification loop helps about as much as its checks cover. Measure it on tests it never sees, or its own success rate will tell you what you want to hear.

Limitations

Ten tasks, written by me, all about following an exact specification. A loop may help more where mistakes crash, or where the visible tests are the whole specification. The ten repeats of one task are not independent, so the p-values are optimistic. The models are small, and the three routes differ: no temperature for Haiku, reasoning that cannot be switched off for GLM. The two GLM runs agree on the gains but not on the level, and I did not record which provider served them. The self-test harness was not run on Haiku.

Run it yourself

The code, the tasks, every answer and every test result are in the repository. Each run writes a results.json with every attempt and a summary.md with per-task results, failure kinds and cost.

python run.py --task-set hard --backend fake    # offline check
python run.py --task-set hard --backend openrouter \
    --model deepseek/deepseek-v4.1-flash \
    --repeats 10 --max-cost 0.90
python run.py --summarize hard_models/deepseek-v4.1-flash
